一、whisper.cpp 的模型文件格式

whisper.cpp 使用 自研 ggml 二进制格式（非 ONNX / GGUF 标准格式，属老版本），由 convert-pt-to-ggml.py 从 PyTorch 权重转换而来。文件结构如下：

┌──────────────────────────────────────────┐
│ magic: 0x67676d6c  ("ggml")             │  4B
├──────────────────────────────────────────┤
│ hparams: 11 个 int32                   │  ~44B
│   n_vocab, n_audio_ctx, n_audio_state,  │
│   n_audio_head, n_audio_layer,          │
│   n_text_ctx, n_text_state,             │
│   n_text_head, n_text_layer,            │
│   n_mels, ftype                         │
├──────────────────────────────────────────┤
│ mel filters: n_mel × n_fft floats       │  ~512KB
├──────────────────────────────────────────┤
│ vocab: n_vocab × (len + string)         │  ~2-3MB
├──────────────────────────────────────────┤
│ tensors:                                │  数十~数百 MB
│   while (!eof) {                        │
│     n_dims, length, ttype (3×int32)     │
│     ne[4] (4×int32)                     │
│     name[length]                        │
│     raw bytes (按 ttype 决定大小)        │
│   }                                     │
└──────────────────────────────────────────┘
  • ftype 编码：ftype = qntvr * GGML_QNT_VERSION_FACTOR + 实际量化类型，加载时 whisper.cpp:1549-1559 拆分版本号与量化类型。
  • 量化模型按 ftype 直接落盘：Q4_0 / Q4_1 / Q5_0 / Q5_1 / Q8_0 的 bit pattern 直接写在文件里，加载就是 memcpy，没有任何反量化步骤——这是性能关键。

二、whisper.cpp 加载流程详解

整体三阶段，代码集中在 src/whisper.cpp：

阶段 1：读取元数据（whisper.cpp:1485-1675）

read_safe(loader, magic);             // 校验 GGML_FILE_MAGIC
read_safe(loader, hparams.*);         // 11 个 int32，得出模型规模
read_safe(loader, filters.n_mel/fft); // mel 滤波器
read_safe(loader, filters.data);      // float 矩阵
read_safe(loader, n_vocab);
for (i = 0; i < n_vocab; ++i) {       // vocab
    read(len); read(string);
    vocab.token_to_id[word] = i;
}

阶段 2：构建 tensor 骨架（whisper.cpp:1684-1846）

与 ONNX 最大的区别之一 whisper.cpp 不解析通用计算图——它在 C++ 代码里硬编码了 Whisper 的所有 tensor 形状： 
const size_t n_tensors = 10 /* input */ + 15 + 15*n_audio_layer + 24*n_text_layer;

然后为每个 layer 创建 encoder / decoder / cross-attn 的 QKV、MLP、LN tensor：

for (int i = 0; i < n_audio_layer; ++i) {
    layer.attn_q_w = create_tensor(..., ggml_new_tensor_2d(ctx, wtype, n_audio_state, n_audio_state), i);
    layer.attn_k_w = create_tensor(..., ggml_new_tensor_2d(ctx, wtype, n_audio_state, n_audio_state), i);
    layer.attn_v_w = create_tensor(..., ggml_new_tensor_2d(ctx, wtype, n_audio_state, n_audio_state), i);
    layer.mlp_0_w  = create_tensor(..., ggml_new_tensor_2d(ctx, wtype, n_audio_state, 4*n_audio_state), i);
    ...
}

create_tensor 内部按 ASR_TENSOR_INFO 表决定算子类型，调用 select_weight_buft 把每个 tensor 分到不同的 backend buffer（GPU / CPU Extra / CPU）。

阶段 3：分配 buffer + 加载权重（whisper.cpp:1848-1951）

// 1) 分配 backend buffer
for (auto & p : ctx_map) {
    ggml_backend_buffer_t buf = ggml_backend_alloc_ctx_tensors_from_buft(ctx, buft);
    model.buffers.emplace_back(buf);
}

// 2) 读取每个 tensor 的原始字节
while (!eof) {
    read(n_dims, length, ttype);
    read(ne[4]); read(name);
    auto tensor = model.tensors[name];      // 按名字查找预创建的张量
    if (ggml_backend_buffer_is_host(tensor->buffer)) {
        // CPU/Metal: 直接 read 到 tensor 内存
        loader->read(ctx, tensor->data, ggml_nbytes(tensor));
    } else {
        // CUDA/Vulkan: 先读到临时 buffer，再 copy 到 device
        read_buf.resize(ggml_nbytes(tensor));
        loader->read(ctx, read_buf.data(), read_buf.size());
        ggml_backend_tensor_set(tensor, read_buf.data(), 0, ggml_nbytes(tensor));
    }
}

关键设计点

设计含义
host vs device 分流host buffer 可以 memcpy 直写 GPU mapping；device buffer 必须 staging buffer
量化数据按 ftype 直读Q4_0 权重就是磁盘上的 GGML_TYPE_Q4_0 字节，没有反量化 CPU 开销
字节序 swapBYTESWAP_FILTERS / BYTESWAP_TENSOR 处理 x86 ↔ ARM 字节序
GGML_BACKEND_BUFFER_USAGE_WEIGHTS标记 buffer 用途，影响后续调度（如可被 graph 复用）
按名字查预建 tensor文件里多/少 tensor、shape 不对都会立即报错（whisper.cpp:1894-1920）

阶段 4：state 阶段再分配 KV cache & 计算图（whisper.cpp:3374）

模型权重加载只完成到「tensor 已有、buffer 分配好」。真正的 GPU 计算图分配在 whisper_init_state：

  • 三个 KV cache（kv_self / kv_cross / kv_pad）
  • whisper_sched_graph_init 预构建 conv/encoder/decoder 计算图
  • Core ML / OpenVINO 外部 encoder 后端按需加载

三、与 ONNX Runtime 的关键区别

维度 whisper.cpp + ggml ONNX Runtime
文件格式 自研紧凑二进制（魔数 0x67676d6c） protobuf 序列化 .onnx（标准算子 + initializer + graph）
模型结构表达 C++ 代码硬编码，文件只含权重与元数据 protobuf 描述完整计算图，ORT 解析后做图优化
加载逻辑 文件流 → 校验 → 预建 tensor → memcpy 权重 protobuf 反序列化 → 算子节点构造 → Initializer 加载 → graph partitioner → EP 选择
量化策略 训练后量化内嵌（Q4_0/Q4_1/Q5_0/Q5_1/Q8_0），权重即量化比特 外部量化工具（onnxruntime-quantize），加载时按算子类型反量化或保持
后端抽象 ggml-backend（CPU/Metal/CUDA/Vulkan/SYCL/OpenCL/CoreML/OpenVINO） Execution Provider（CPU/CUDA/DirectML/TensorRT/OpenVINO/CoreML/DML/ROCm/…）
计算图 每个任务手写 whisper_build_graph_* 自动构建通用 ONNX graph，可做算子融合、constant folding
内存管理 自管 backend buffer + arena allocator 默认 arena + memory pattern 优化
动态 shape 不支持静态图外的新 shape 支持 dynamic axes（虽然 transformer 通常固定）
模型验证 名字 + shape + 元素数三重校验（缺一即报错） ONNX checker + ORT 自己的 shape inference
本质上
  • ONNX Runtime 是通用推理引擎——一份 .onnx 跑任意模型
  • whisper.cpp 是专用推理器——只为 Whisper 这一种 transformer 编写的 C++ 代码

四、相同后端下的性能对比

结论 在 GPU/CPU 同后端、相同量化等级下，whisper.cpp 通常略快或相当，但优势不显著。

1. whisper.cpp 优势场景

（1）计算图精简，开销更低

  • 没有 ONNX Runtime 的算子 dispatch、shape inference、动态内存分配开销
  • whisper_build_graph_* 是手写的高效图，节点数量比通用图少很多

（2）量化更激进

  • ggml 支持 Q4_0/Q4_1/Q5_0/Q5_1/Q8_0，最深的 Q4_0 把 large 模型压到 ~750MB
  • ONNX Runtime 的 uint4 量化支持相对晚，且部分算子不支持
  • ggml 的量化是内置原生 kernel（CUDA/Metal 都有手写 Q4_0 GEMM），不走通用反量化

（3）内存模型更紧凑

  • KV cache 大小、buffer 复用都是为 Whisper 量身定制
  • 没有 ONNX Runtime 的 IO binding、session state 通用管理开销

（4）手写 kernel

  • Metal / CUDA 后端有针对 Whisper shape 优化的手写 attention、conv kernel
  • 例如 ggml-cuda 的 flash attention 实现针对 n_text_ctx=448/1500 等典型 Whisper 值优化

（5）启动延迟更低

  • whisper.cpp：几百毫秒即可加载完 large 模型
  • ORT：protobuf 反序列化 + graph partition + EP init 通常更慢

2. ONNX Runtime 优势场景

（1）算子库丰富

  • 支持任意 ONNX 模型，不只是 Whisper
  • 新模型、新算子不需要改 C++ 代码

（2）自动图优化

  • 算子融合（如 LayerNorm + MatMul）、constant folding、layout 转换自动完成
  • 对未手动优化的模型效果好

（3）持续维护

  • Microsoft + 社区持续更新，新硬件新指令集支持更及时
  • whisper.cpp 依赖 ggml 仓库的更新节奏

（4）跨框架兼容

  • 一份 .onnx 可以在 ORT / ONNX.js / onnxruntime-mobile / SNPE / TensorRT 等多个 runtime 上跑
  • whisper.cpp 模型只能在 ggml 系列（whisper.cpp / llama.cpp / 其他 ggml 项目）使用

3. 实测经验值（参考社区数据）

在 Apple M2、large-v3 模型、相同 Metal 后端、相同 Q5_1 量化下：

指标whisper.cpp (Q5_1)ONNX Runtime (Q5_1 via CPU/CUDA EP)
30s 音频推理~3-4s~4-6s（CPU EP）/ ~3-4s（CUDA EP）
加载时间~0.3s~1-2s
内存占用~1.2GB~1.5GB
注意
  • 这些数字高度依赖模型版本、量化等级、batch size、beam size
  • ORT 启用 TensorRT EP 后通常能追上 whisper.cpp 的 CUDA 后端
  • 在 CPU only 场景下，whisper.cpp 的手写 AVX/NEON kernel 比 ORT 的 CPU EP 通常快 20-50%

4. 选择建议

场景推荐
只需要 Whisper、追求极致性能/小体积whisper.cpp
需要一套推理引擎跑多种模型（Whisper + LLM + 其他）ONNX Runtime
部署到 Apple Silicon 移动端/iOSwhisper.cpp（Metal 路径优化更好）
部署到 Android、跨平台 SDKONNX Runtime（NNAPI EP）
需要 TensorRT / 生产级 NVIDIA 部署ONNX Runtime + TensorRT EP
研究/实验、需要频繁换模型结构ONNX Runtime（图优化自动）

五、小结

whisper.cpp 的模型加载是「手写硬编码 + 直接 memcpy 量化比特 + 后端 buffer 分流」三件套，本质上是把 Whisper 模型结构的全部知识烧进了 C++ 源码；ONNX Runtime 是「通用算子库 + 自动图优化 + 多 EP 后端」的工程化方案。

性能上 whisper.cpp 在专用场景有 10-30% 的领先优势（量化更激进、图更精简、kernel 更专用），但 ONNX Runtime 在通用性和维护性上完胜。如果只为跑 Whisper，选 whisper.cpp；如果推理栈要服务多种模型，选 ONNX Runtime。
